Includes & Layouts

Mutor does not provide a dedicated layout system. Instead, it provides a partial and component system through Mutor::include().

While this may sound limiting at first, nested includes are usually all that is needed to build page shells, reusable navigation, cards, dashboards, and other complex layouts. Rather than introducing a separate layout abstraction, Mutor focuses on composition and leaves structure entirely in the hands of the application.

Including Partials

Partials are included using Mutor::include(). The first argument identifies the component to include while the optional second argument specifies the context that should be used when rendering that partial. If no context is supplied, the current execution context is reused automatically.

Included templates may themselves include other templates, making it possible to compose larger structures from smaller reusable pieces. Mutor supports nested includes and keeps track of inclusion chains to prevent cyclic inclusions from causing infinite recursion. 

\{{ Mutor::include("header") }}

\{{ Mutor::include("user-card", user) }}

Includes themselves are synchronous. However, if an included template contains asynchronous operations through Mutor::await(), the include may return a promise. In such cases the include can be wrapped in Mutor::await() to resolve the result before rendering continues. 

\{{ Mutor::await(
  Mutor::include("profile")
) }}

Only do this when the included template is known to be asynchronous.

Registering Components

In standard Mutor environments, components can be registered directly on the instance. Registration stores the template in Mutor's internal component cache and makes it available for both direct rendering and inclusion.

Once registered, a component can be rendered using renderComponent(). Components containing asynchronous operations must instead be rendered using renderAsyncComponent() and awaited. 

mutor.registerComponent(
  "header",
  "<header>\{{ title }}</header>"
);

const html = mutor.renderComponent(
  "header",
  context
);

const asyncHtml =
  await mutor.renderAsyncComponent(
    "header",
    context
  );

Attempting to include or render a component that has not been registered results in an error. Registration may also fail when the component cannot be stored within the configured cache limits.

Cache size can be configured through the instance options. More information can be found in the Configuration documentation.

Server-Side Includes

Server-side includes work differently from component includes. Instead of resolving component names, Mutor resolves templates directly from the filesystem. When an include is encountered, Mutor determines the location of the including template, resolves the requested path to an absolute location, and uses that absolute path as the cache key.

If the template has already been compiled, the cached version is reused immediately. Otherwise, Mutor reads the file from disk, compiles it, stores it in the cache, and then renders it.

Because includes are resolved through the filesystem, relative paths are supported naturally. Mutor also supports @/ aliases which resolve relative to the configured baseDir. 

new Mutor({
  baseDir: "./views"
});

\{{ Mutor::include("./partials/header.html") }}

\{{ Mutor::include(
  "@/components/header.html"
) }}

Unlike the standard Mutor runtime, the server implementation does not expose registerComponent(). This is an intentional design choice and means component registries must be managed externally when required.

If a referenced file cannot be found, the underlying filesystem error is surfaced as a Mutor error.

Handling Include Errors

Failed includes throw by default and terminate the current rendering operation. This behavior can be changed using the onIncludeFail option.

Setting the value to "ignore" skips failed includes silently, while "ignoreLog" skips the include and reports the failure. When either option is used, Mutor invokes onIncludeError() and passes metadata describing the failed inclusion.

Forgive the naming convention. Lol. 

new Mutor({
  onIncludeFail: "ignoreLog",

  onIncludeError(meta) {
    console.log(meta);

    return "<!-- unavailable -->";
  }
});

The metadata contains information about the include that failed, including the source template, requested path, and resolved absolute path when available. 

{
  from: string;
  path: string;
  absolutePath?: string;
}

Whatever value is returned from onIncludeError() is inserted into the output in place of the failed include.
